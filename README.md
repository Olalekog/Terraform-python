# Terraform + Python cross-account CI/CD IAM

Reusable target IAM role module, a source role assumption policy, and a Python helper that verifies source and destination identities. Terraform creates the authorization path; Python uses STS temporary credentials to run deployment commands.

## Authorization pattern

1. A CI runner authenticates to an existing source-account role (GitHub OIDC, EC2 instance profile, or another federated role).
2. The source role has `sts:AssumeRole` permission on one exact target role ARN, conditioned on the matching external ID.
3. The target role trusts that exact source role, also conditioned on the external ID.
4. Python validates the source identity, assumes the configured target, verifies the resulting identity, and passes temporary credentials only to the child process.

The sample allows `s3:GetObject` and `s3:PutObject` under `releases/dev/*` in one existing target-account bucket, plus prefix-constrained `s3:ListBucket`. It does not grant object deletion, IAM administration, or infrastructure provisioning. Adapt the permission statements to the actual pipeline task.

An external ID mitigates the confused deputy problem; it is not a password and is visible in IAM policies and Terraform state. Use a unique value per customer/target integration, assigned by the party operating the pipeline. Reusing one value across unrelated customers defeats its purpose. It does not protect against compromise of the trusted source role.

## Files

- `modules/cross_account_role/`: target role, trust policy, scoped inline permissions, optional permissions boundary, and generated source policy.
- `examples/bootstrap/`: two account-specific AWS provider configurations; creates the target role and attaches the caller policy to an existing source role.
- `python/assume_role.py`: importable helper and CLI with an environment-to-role allowlist.
- `.github/workflows/artifacts.yml`: GitHub OIDC example, run on every push to `main` or by hand.
- `tests/`: mocked STS authorization/identity tests and HCL parsing.

## Prerequisites

Terraform 1.6+, Python 3.10+, AWS CLI v2 for the sample command, two AWS accounts, an existing source pipeline role, an existing target S3 bucket, and separate bootstrap administrator profiles with permission to manage these IAM resources. Bootstrap profiles are only for setup. The runtime role cannot create or modify its own authorization.

The example bucket should be in the target account and use SSE-S3. For SSE-KMS, explicitly add required operations on the exact KMS key ARN and review its key policy; restrict use with `kms:ViaService` and appropriate encryption context. Multipart uploads may require additional narrowly scoped S3 actions; the README upload is small. Bucket policies, SCPs, permissions boundaries, and other explicit denies can block access.

## Bootstrap

From the project root (Bash / Git Bash):

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
cp examples/bootstrap/terraform.tfvars.example examples/bootstrap/terraform.tfvars
# Edit account IDs, role name, profiles, and bucket name before continuing.
export TF_VAR_external_id="$(python -c 'import uuid; print(uuid.uuid4())')"
# Record this value securely as CICD_DEV_EXTERNAL_ID in the pipeline environment.
terraform -chdir=examples/bootstrap init
terraform -chdir=examples/bootstrap fmt -check
terraform -chdir=examples/bootstrap validate
terraform -chdir=examples/bootstrap plan -out=bootstrap.tfplan
terraform -chdir=examples/bootstrap apply bootstrap.tfplan
terraform -chdir=examples/bootstrap output -raw source_role_arn
terraform -chdir=examples/bootstrap output -raw target_role_arn
```

Preserve the generated external ID across future plans; generating a new one rotates the trust requirement. Bootstrap runs locally by default. Before shared/team use, configure an encrypted remote state backend with locking and restrict access to state and saved plans. Terraform `sensitive` redacts normal output but does not encrypt state. Never commit state, plans, or tfvars. Commit the Terraform provider lock file generated by `init`.

Copy `python/targets.example.json` to `python/targets.json` and replace both role ARNs with the outputs. The configuration has no secret values and must be reviewed as part of code changes. Copy the target configuration into your repository for the GitHub workflow; it is ignored by default to prevent accidental commitment of unfinished placeholders. To deliberately commit the reviewed configuration, use `git add -f python/targets.json`.

## Python runtime

Authenticate as the configured source pipeline role first. A local SSO login often gives a different role; configure an AWS CLI profile that assumes the pipeline source role if local use is required and permitted. The helper intentionally rejects a different source role, including administrator or IAM user credentials.

```bash
export AWS_PROFILE=pipeline-source
export CICD_DEV_EXTERNAL_ID="$TF_VAR_external_id"
python python/assume_role.py --config python/targets.json --target dev \
  --session-name local-build-001

python python/assume_role.py --config python/targets.json --target dev \
  --session-name local-build-001 --duration 900 -- \
  aws s3 cp README.md s3://YOUR-BUCKET/releases/dev/build-001.md
```

Without a command, the CLI prints only the target role ARN and expiration. With a command, it preserves the command's exit code and uses an argument list without shell evaluation. Only execute trusted deployment commands: they receive credentials and can print them if instructed. The parent process does not modify its environment or write credential files.

For direct Boto3 use, import `Target` and `assume` from `python/assume_role.py`:

```python
from assume_role import Target, assume
session, expiration = assume(
    Target("arn:aws:iam::111111111111:role/github-pipeline",
           "arn:aws:iam::222222222222:role/cicd-artifact-dev",
           "CICD_DEV_EXTERNAL_ID"),
    session_name="build-123",
)
session.client("s3").put_object(
    Bucket="YOUR-BUCKET", Key="releases/dev/build-123.txt", Body=b"artifact")
```

Add `python/` to your import path for this example. Credentials do not auto-refresh. Finish each command within the selected 900-3600 second session, or split a long job into separate assumption steps. Role chaining is limited to one hour. STS uses standard SDK retries for transient errors; the helper does not retry authorization denials. After Terraform apply, IAM propagation may briefly delay first use.

## GitHub Actions configuration

In the existing source role's OIDC trust policy, use the exact repository/environment subject and audience; the role and OIDC provider must already exist. Example trust statement (replace account, organization, and repository):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Federated": "arn:aws:iam::111111111111:oidc-provider/token.actions.githubusercontent.com"},
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {"StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:YOUR-ORG/YOUR-REPO:environment:dev"
    }}
  }]
}
```

Use GitHub environment protection and allowed deployment branches because environment subjects do not encode a branch.

The workflow reads these repository variables (Settings > Secrets and variables > Actions > Variables):

| Variable | Example | Used for |
| --- | --- | --- |
| `AWS_ACCOUNT_ID` | `866934333672` | The source role's account; credentials for any other account are refused |
| `AWS_REGION` | `us-east-1` | Region for the source role's credentials |
| `ENVIRONMENT` | `dev` | The GitHub environment the job runs in, the `python/targets.json` entry, and the upload prefix `releases/<env>/` |
| `PROJECT_NAME` | `terraform-python` | AWS session names and the uploaded file's name |
| `ROLE_TO_ASSUME` | `arn:aws:iam::866934333672:role/Reactjs-application-role` | The source role GitHub signs in as; must equal that target's `source_role_arn` in `python/targets.json` |

The `dev` GitHub environment also needs the secret `CICD_DEV_EXTERNAL_ID` and the variable `ARTIFACT_BUCKET`. The workflow's first steps stop with a named error if any of these is missing, if `python/targets.json` is missing, or if `ROLE_TO_ASSUME` does not match it. Commit the reviewed `python/targets.json`. The included workflow uploads this README as a small artifact. Replace that command with the real build artifact and corresponding scoped permission set. The workflow uses the included exact Python dependency snapshot. Pin action references to reviewed commit SHAs before production adoption and periodically update the dependency snapshot.

## Reuse for dev, UAT, and production

Instantiate the module once per target account/environment with its target provider alias and unique external ID. Attach each generated caller policy to the source role using unique policy names. Add `uat` and `prod` entries to the Python allowlist with separate external ID environment variables. Prefer separate source roles for production isolation; protect production jobs with environment approvals and branch restrictions.

The permissions input supports conditions and explicit actions/resources. It rejects wildcard actions and global resource `*`; a single trailing resource prefix wildcard is permitted for object paths. This validation cannot determine business-level least privilege. Review every action, resource, and condition; avoid privilege-escalating IAM permissions and overly broad ARN prefixes. APIs requiring `Resource: "*"` are intentionally outside this module's contract.

An optional permissions boundary can further constrain the target role. A boundary does not grant access. This module owns its own inline policy, but it does not remove other policies attached by another actor. Review the source and target roles for unrelated permissions and enforce configuration drift controls. Recreating the source role may require reapplying target trust because IAM stores a role principal ID.

## Verification

```bash
python -m pytest -q
terraform fmt -recursive -check
terraform -chdir=examples/bootstrap init -backend=false
terraform -chdir=examples/bootstrap validate
# Terraform 1.7+ is required for the test override_data feature:
terraform -chdir=modules/cross_account_role init -backend=false
terraform -chdir=modules/cross_account_role test
```

Terraform plan tests assert exact principal and external ID trust, prefix-scoped permissions, and rejection of unsafe inputs; they use an overridden identity data source and do not call AWS. Python offline tests cover exact STS request parameters, missing IDs, invalid roles, mismatched identities, duration limits, AWS denial, child credential isolation, and exit codes. These tests do not prove real AWS authorization.

After bootstrap, validate in a sandbox using the configured source role:

- Correct external ID: role assumption succeeds; the scoped artifact upload succeeds.
- Wrong external ID: `sts:AssumeRole` is denied. The missing-ID case is rejected by Python before an API call.
- A different source principal: direct STS assumption is denied by target trust even if its own policy allows the ARN.
- Upload outside `releases/dev/`: denied, provided no additional permissions are attached to the role.
- Bucket listing with `--prefix releases/dev/`: allowed; unrelated prefixes denied.
- `s3:DeleteObject`: denied, provided no additional grants exist.

Record run IDs in session names and inspect CloudTrail STS and deployment events. Object-level S3 auditing requires appropriate CloudTrail data events. Test outside-prefix writes with disposable object names in a sandbox so an unexpected existing grant cannot affect production objects. Use IAM Access Analyzer policy validation and access evidence to refine the permission set.

To remove this example, review `terraform destroy` using the same bootstrap profiles and external ID input. It removes only the managed role and inline source policy; the existing bucket and source role are not managed by this example.
